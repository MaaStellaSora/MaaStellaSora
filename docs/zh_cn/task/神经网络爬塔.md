# 爬塔（神经网络）

## Pipeline 构成与覆盖

神经网络爬塔复用原版爬塔的 Pipeline 作为主流程：出发、进入星塔、楼层探索、战斗和页面导航仍由原节点及其 `next` 关系驱动。任务在 `assets/interface/tasks/climb_tower_neural.json` 中声明专用入口，并通过任务级 `pipeline_override` 覆盖少数节点的识别或动作；专用 Pipeline 只补充神经网络入口、识别辅助和刷新等节点，不复制整套爬塔流程，也不修改共享的原版 Pipeline 文件。

主要覆盖点如下：

- `星塔_入口_agent` 将原准备动作替换为神经网络准备回调，并从专用入口接入原有出发流程；`星塔_跳过进入星塔流程_agent` 禁用，`星塔_星塔探索按钮_agent` 的后继改为属性塔选择，固定走主页启动路线。
- `星塔_编队角色_选择队伍_agent` 的动作改为 `DoNothing`，跳过原自动选队；`星塔_编队秘纹_agent`、`星塔_开始爬塔_检测背包按钮_agent` 和 `星塔_点击空白处关闭_agent` 分别接入音符开始、场景确认和音符继续回调，处理模型所需的状态与页面转换。
- `星塔_节点_选择潜能_agent` 改由模型识别并决策，领取节点 `星塔_节点_选择潜能_拿走_agent` 改为确认潜能领取；事件节点 `星塔_节点_进行对话选择_agent` 改用模型识别选项，并由自定义动作处理点击。
- `星塔_节点_商店_商店主流程_agent` 改由模型商店逻辑处理；`星塔_记录界面_读取数值_agent` 扩展结算页识别条件，并使用神经网络结算读取回调。
- `星塔_循环用节点_agent` 替换为神经网络循环回调，按所设爬塔次数维护对局边界；其余后继流程仍使用原节点关系。

因此，这里的“覆盖”主要是按任务替换节点行为或少量路由，不是重写爬塔主流程。普通新版爬塔任务不应用这些覆盖，继续使用原有节点逻辑。

Windows x64 原生游戏的国服、日服可从主页启动此任务，选择属性塔和爬塔次数。首次进入核心潜能页时从背包读游戏内预设；同一任务的后续对局复用目标，各局单独记录持有和库存。原有爬塔任务不受影响。

专用 Pipeline 负责导航、点击和等待；`agent/custom/climb_tower_neural/` 负责识别结果、推理和记录。名称、区服文字、事件和音符规则分别在目录与 Pipeline 的配置中维护。

## 节点逻辑详解

以下按一次对局的执行顺序说明任务覆盖节点。Pipeline 节点负责在合适的画面触发回调；节点名到 Agent 注册名、回调类的映射见 `agent/custom/climb_tower_neural/agent_bindings.json`，回调实现集中在 `agent/custom/climb_tower_neural/agent_callbacks.py`。除完整路径另有说明外，各节列出的 Python 模块均位于 `agent/custom/climb_tower_neural/`；共享的页面识别、模型状态、音符账本和记录器由各自模块承接，因此每节只列该逻辑的主要实现文件。

### 1. 从主页进入：入口和路线

专用入口 `星塔_神经网络_入口` 识别主页出发按钮后转到原版 `星塔_入口_agent`。任务覆盖把该节点的原准备动作换成 `stella_value_preparation`（`Preparation`），并将后继明确设为 `星塔_出发_agent`。原版的 `星塔_跳过进入星塔流程_agent` 被禁用，`星塔_星塔探索按钮_agent` 的后继固定指向属性塔选择，因此该任务按主页启动路线进入星塔，而不是复用原版的“已在星塔中”跳过路径。属性塔选项进一步覆盖 `星塔_属性塔选择_agent` 的图片模板，并把塔对应的两种 `active_melodies` 写入节点 `attach`；后续音符识别据此知道哪些音符属于本塔。

`Preparation` 首先确认当前确实是神经网络模式，再检查功能开关、语言和 `星塔_神经网络_运行环境` 上的 `native_windows`。通过检查后调用基类 `AscensionPreparation`，沿用原有的事件答案规则加载、潜能参数检查和可选状态重置；成功后才调用运行时开始本次任务。准备阶段验证任务能否启动并准备通用规则。模型和本局追踪器延迟到第一次潜能页初始化，神经网络任务据实际游戏队伍建立目标。

主要文件：`assets/interface/tasks/climb_tower_neural.json`、`assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`、`agent/custom/climb_tower_neural/agent_bindings.json`、`agent/custom/climb_tower_neural/agent_callbacks.py`、`agent/custom/climb_tower_neural/maa_hook.py`、`agent/custom/climb_tower/climb_tower_preparation.py`。

### 2. 编队和开局：保留队伍、建立音符基线

`星塔_编队角色_选择队伍_agent` 的动作覆盖为 `DoNothing`，保留玩家当前队伍，不调用原版的自动选队函数。其余编队界面仍由原 Pipeline 导航。

`星塔_编队秘纹_agent` 使用 `stella_note_start`（`NoteStart`）。采集器启用时（配置允许且本任务的本地记录或上传选项要求采集），回调先在开始按钮仍可见时读取开局配置：塔类型来自属性塔节点的 `active_melodies`，开局音符供应和主音符从当前界面识别；无法读清的值保持未知，不以默认库存补齐。之后才点击开始按钮，并登记“已点击、等待进入”的意图。`星塔_开始爬塔_检测背包按钮_agent` 以 `stella_note_scene`（`NoteScene`）确认进入爬塔场景，运行时据此提交开局记录并创建本局音符账本、首场战斗边界。把“按钮已点击”和“已进入本局”分开，是为了避免动画、点击失败或中途退出造成幽灵对局。

账本以开局读数为基线，后续只比较同一音符在前后可靠快照中的变化；它不会把某次页面没显示的音符当成零，也不因一次局部 OCR 失败而沿用旧数值冒充新观测。若本地记录和上传采集均关闭，开始回调仍执行原点击，但不进行音符采集；上传授权与本地记录开关是不同设置。

真实进塔确认同时开始 `RunSession`。它保存运行所需的开局、楼层和钱包事实，以及当前操作和购买钱包的关联，不依赖采集器是否启用或记录是否写入成功；按钮点击和待确认的开局图像仍由运行时暂存。当前任务边界和每次爬塔循环都会清空会话，不把这个内存会话当成跨任务接续实现。

主要文件：`agent/custom/climb_tower_neural/agent_callbacks.py`、`maa_hook.py`、`session.py`、`note_runtime.py`、`note_setup_reader.py`、`note_ocr.py`、`note_ledger.py`；识别开局状态使用的场景和交互节点在 `assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`、`climb_tower_neural_note.json` 中。

### 3. 首次潜能页：读取预设并初始化模型状态

`星塔_节点_选择潜能_agent` 的识别器覆盖为 `stella_value_potential`（`Potential`）。新任务首次到达潜能页时，运行时打开背包读取三名角色和各自的潜能目标、等级及已有数量。每名角色须读齐 4 张核心、3 张稀有和 9 张普通潜能，品质、槽位、目标与持有等级须符合背包布局。正式库内角色的目标名称仍须独立确认；队伍中支持一个库外角色，其标题须有可信 OCR，16 张卡须各有非空 OCR 文本，但允许重名、错名，以“角色槽位＋品质＋背包显示序号”建立独立本地身份，名称只作观测，不冒充正式潜能 ID，也不覆盖正式目录。

最后一帧的单卡裁图也可能补足角色识别所需的两票。背包读取器按最新名称证据判断角色，再用保留的截图补确认已滚出视野的卡名。

Windows 的 WithCursorPos 控制器会在松手时把鼠标送回按下前的位置。开始读背包时，若鼠标位于游戏窗口，`bag_cursor.py` 先将其停在客户区左上角，让翻页和选卡后的归位点避开卡名及徽标。鼠标在其他窗口时不移动。

点击「潜能收集」后，角色标题或同时可见的列表滚动条和「全部」开关可确认已进入列表。画面仍显示秘纹技能页时，重新定位「潜能收集」并补点一次。读取背包时使用「全部」视图，约定游戏内已开启「显示推荐」。没有推荐徽标的卡记为零目标。首张核心卡默认选中，绿色选框会遮挡列表徽标，读取右侧详情的推荐徽标可避开遮挡。其他卡读取列表徽标，带等级的目标从徽标右侧读取数字。当前页只有一张卡名始终读不清时，选中该卡并确认右侧标题，再继续滚动。

`preset_tool.py` 把确认后的背包内容编译成模型预设：目标集合描述要追求的潜能，初始库存描述开局已经持有的潜能，两者不混为一谈。角色标题只拼接同一帧的文字，取各片段最低置信度。多帧读数优先采用达到 0.85 的标题，以免早先的低分错字挡住新角色预设编译。在同一置信度档内优先保留较完整的名称，等长时采用分数较高的一帧。之后运行时加载 `model.json` 指定的模型，建立每局独立的 `ObservationTracker`，把持有情况和潜能池身份投影到模型状态。潜能池中哪些卡还可能出现会影响未来抽取模拟；如果池中身份齐全但实际池序不可知，则保留已观察到的位置，其余按预设目录顺序构造估值所需池序。该顺序只是模型输入，不会作为“实读的游戏池位”记录。整池展示时，只有已经确认的位置能约束身份匹配；新读清的卡名和推荐等级可以纠正先前推测的位置。

首次读完三名角色后，若全队推荐目标为零，任务停在背包并提示检查预设和「显示推荐」。只要有一张卡设了目标（含核心潜能），返回原潜能页后即可启动模型。同一任务的后续对局复用目标预设，重新初始化持有、路线和商店状态。若仅为补采背包中的秘纹技能和音符而开包失败，确认仍在原潜能页即可继续，并将这次背包观测记为不完整。

详情补读要求目标卡选框、列表未滚动及连续两帧相同的清晰标题。选框可能先于详情更新，因此标题与上一张相同时，还需目标卡自身置信度至少 0.85 的列表 OCR 同名证据；不同角色可以持有同名潜能，不能一律等待标题改变，也不能仅凭旧标题连续出现就判为切换完成。若列表卡名完全缺读、同名标题等待超时，则先选当前页已确认且完整可见的不同名卡，确认其选框和详情标题后再返回目标，以真实标题变化确认详情刷新。过渡只用于同名等待失败，不增加正常补读的点击。

主要文件：`agent_callbacks.py`、`maa_hook.py`、`bag_preset_reader.py`、`preset_tool.py`、`provisional_cards.py`、`data/potential_name_catalog.json`、`data/character_name_catalog.json`、`data/bag_preset_rules.json`、`observation.py`、`pool_identity.py`。

### 4. 潜能页：识别候选、估值、选择和刷新

道具提示仍在屏幕上时，潜能回调也直接读取候选数量、品质、钱包、刷新费用，以及每张卡的名字、旧等级、新等级和推荐标记。提示可能持续到卡片已经可读，是否重读取决于候选字段本身。`potential_reading.py` 整理 OCR 和模板结果，`ModelPotentialHandler` 结合预设目录、角色、品质和持有等级识别卡片。分行卡名取自同一次 OCR。候选缺读、等级冲突、品质布局变化或钱包冲突时重读，仍不能形成完整输入就停止。

潜能页按拇指图标定位，读取左侧完整推荐标签。国服显示「推荐6级」，日服数字在标签前部；只截左侧会漏掉国服的等级。数字与标签下方的持有进度分开读取。

普通潜能页候选通常属于同一角色，可用队伍目标和旧等级消歧；强化页可能混合角色，代码会比较角色图像和已知持有信息。整页能匹配同一库内角色时沿用正式身份。若只有个别卡名命中队友，且这些名字也出现在库外角色背包中，则用整页其余候选区分归属，例如琥珀和卡西米拉的「弱点标定」。库外角色按品质、持有旧等级和推荐标记筛选槽位，再整页比较名称。徽标可见但数字缺读时，仍可匹配背包中已设目标的槽位，模型取该槽位的背包目标。若推荐读数使整页无法对应，则仅放宽推荐条件，并将这次库外绑定标为估计。同分时按稳定槽位顺序确定性分配并标为估计，允许继续模型决策。同局再次看到暂定名称时可用它区分同分槽位，重复读到同一个名字不会把估计变成已确认。正式角色目录只读。

背包错字有时会掩盖库外卡与队友的同名关系。普通页由同一角色出卡，可结合整页卡名判断归属。库外卡在潜能页确认名字后，后续按可信别名匹配。强化页可能同时出现两个角色的同名卡，用同局缓存的角色头像区分归属后，再分配其余槽位。

强化页若只读到「弱点」这样的卡名前缀，先用头像定位库内队友，再核对其已持有卡的品质、等级和推荐目标。唯一对应时可继续强化，并记录名称来自推断；有多张符合时重读。

首次领取时若只能看清推荐徽标，多个不同目标的槽位可能都符合。后续升级读清卡名和推荐等级、能确定真实槽位及先前错记的持有时，在估值前一起纠正持有和剩余池。例如目标 6 的卡从 2 升到 3，应计 1 级有效潜能。连续奖励中，即使两页等级排列相同，新页上独立确认的角色或卡片变化也能证明上一次领取成功。仅重新分配本地槽位不足以确认换页。

相关研究未点满时，同一强化页可以同时出现升一级和升两级的卡。模型按每张卡显示的旧等级和新等级分别估值，确认领取后才按所选卡的新等级更新持有记录。混合页无法计作一次全页翻倍。5 升 6 已到等级上限，单凭这张卡也无法判定是否触发翻倍。

模型状态包括当前路线位置、金币、已持有等级、目标潜能以及可能的抽取池；决策前要求路线位置和完整潜能身份目录都可用。核心潜能按队伍目标规则优先选择仍有目标等级的卡，不让普通潜能价值模型替代这一专门规则。普通潜能则把当前可选卡与经济上可执行的刷新一起作为候选动作，比较动作对终局普通潜能得分的预期变化并选择价值最高者。该模型的目标是普通潜能收益，不是整局战斗胜率；它没有“最低收益门槛”或置信度拦截。候选日志中的“预期”表示选择后的终局估值，变化行相对于上一次预期；第一次则以开局估值为基准。

若选择结果是刷新，回调把后继临时改为 `星塔_神经网络_潜能刷新`。刷新动作成功返回并不等于页面刷新成功：实现还要确认金币扣减符合刷新费用、候选数量/品质布局重新出现，才增加刷新次数并重新进入潜能识别。付费刷新超时后，从新截图读取钱包。余额仍与点击前相同才补点一次。余额读不清，或等待期间已经读到过余额变化，就不再补点，以免重复扣费。本任务把可刷新次数上限设为很大、保留金币设为零，因此实际可刷新性主要由费用是否已确认、当前金币是否付得起及模型对刷新动作的估值决定；无法确认刷新结果会停止本次任务。核心潜能页或强化页等不适用刷新费用的页面不会凭空加入刷新动作。

主要文件：`agent_callbacks.py`、`potential.py`、`potential_reading.py`、`observation.py`、`potential_adapter.py`、`value_model.py`、`critic/`、`tower_sampling_collector.py`。`agent/custom/climb_tower/climb_tower_potential/` 下的上下文、识别参数和卡片布局由标准爬塔模块提供并复用。刷新和潜能 OCR 辅助定义在 `assets/resource/base/pipeline/climb_tower/climb_tower_neural_potential.json`、`climb_tower_neural_numbers.json` 和 `climb_tower_neural.json`。

钱包若已确认扣除刷新费，即使候选布局最终缺读，也立即保留真实余额，并在刷新回调停止前同步模型金币；刷新次数与候选布局仍只在整页确认后提交，避免失败动作记录和导出沿用扣款前余额。

### 5. 潜能领取：确认操作后再更新状态

模型识别阶段先选中卡片并暂存一份“待领取”记录，但这时不会更新模型的持有库存。Pipeline 随后进入 `星塔_节点_选择潜能_拿走_agent`；神经网络覆盖把该节点的识别设为 `DirectHit`，由 `stella_value_potential_take`（`PotentialTake`）负责完成真实领取。回调会再次读取卡片页签名、所选卡片和“拿走”按钮，确保屏幕仍是刚才作出决策的同一页；必要时重新选中目标卡，然后点击按钮。

点击后等待原卡页/按钮的消失及下一页的稳定出现，以区分“点击已经发送”与“领取已经发生”。如果新页暂时读不清，会结合原卡和按钮消失、下一页重新出现的证据确认换页；如果原页重新读清，则视为上一次领取未确认，继续有限重试。只有确认离开原页后才提交潜能持有等级、身份池和采样记录；未确认时保留未知状态并停止任务，避免重复领取或把未成功的选择当作已持有。

已确认的潜能持有由 `ObservationTracker` 维护；领取提交只更新该追踪器，不另建原版 `OwnedPotentials` 缓存。`PendingPotentialTake` 保存待领取页及确认状态，不能作为第二份持有库存。研究记录仍由采集器按已确认操作生成。

潜能页缓存也由追踪器管理。`commit_potential_take()` 按原顺序提交选择、标记本次领取已提交，再调用 `close_potential_page()` 结束当前页；UI 确认代码不逐项修改追踪器的私有缓存。即使下一奖励页的卡片签名和金币相同，也必须按新页处理。商店购买的返回页仍由领取确认代码根据实际页面证据登记，不在清理模型页缓存时推断。

主要文件：`agent_callbacks.py`、`potential.py`、`potential_reading.py`、`observation.py`、`tower_sampling_collector.py`；领取之后的流程节点仍由 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json` 调度。

### 6. 事件：完整读取菜单后决策，确认点击转换

事件节点 `星塔_节点_进行对话选择_agent` 同时覆盖识别和动作。`stella_value_event`（`Event`）沿用官方事件读取器的区域和选项定位方式，并记录每个问题、选项文字及后果来自哪次 OCR、是否完整。只有完整可见菜单才用于模型决策；选项未显示、文字未读清、后果有缺失或同一菜单读取冲突时会等待重读。事件页不显示楼层，不能把菜单所在时刻当成楼层实读。

普通事件通过事件映射把文字菜单对应到已知事件及游戏选项，再结合当前钱包、潜能状态和路线状态生成可执行选项。模型按各结果概率评估事件选项对后续潜能收益的期望；如果事件楼层存在多条可能路线（例如首层追加事件之后仍可能遇到二层固定事件，二层事件之后才进入三层战斗），会保留多个路线候选并按概率合并估值，而不是挑一个“看起来最像”的楼层。此时决策记录的楼层留空并保留候选；之后的事件奖励潜能页也沿用这些路线候选，不能把估值用的代表路线写成实读楼层。对于随机结果可能造成金币不足、选项已禁用或成本超过当前钱包的选项，会按可执行性排除或标记不评估。

已匹配的答题事件不交给模型选答案，而是按准备阶段载入的官方答案规则匹配问题、选项和后果；答案唯一确认后沿用该规则选择。答题匹配允许当前暂时读不到金币，因为答案本身不依赖钱包；但后续奖励页的余额只用于同步下一次金币变化，不能反推事件楼层。普通事件未映射、模型输入不完整或答题答案未匹配时停止任务，不返回默认选项。

识别器返回选中选项框，由 `stella_note_event_click`（`NoteEventClick`）执行点击。若该事件可能消耗音符，先检查账本里的操作前库存。需要开包补读时，返回后重新识别菜单，核对问题、所有选项和目标选项，再用新框点击一次。点击后等待最多 30 秒，连续两帧确认同一后续页面才提交事件并清除缓存。临时提示和加载共用这段时间。到期仍未确认就提示超时并停止，避免再次点击已生效的选项。

事件识别与点击共享 `ObservationTracker.event_page_cache` 这一份当前选择；`ValueModelRuntime` 不保存副本。`events._finish_event_result()` 将已选择的 UI 索引与最终识别详情一起存入缓存。完整菜单和钱包均未变化时，仍复用原决策并更新本次按钮框；钱包或菜单变化则按原事件事务重新估值。缓存属于当前未完成的菜单，模型的 `_event_transaction` 负责暂存求值结果，待点击转场确认后才提交，两者不能相互替代。

可选研究记录通过 `event_menu(question, choices)` 接收同一次读取的问题与选项，不再先写一个临时问题字段。`event_choice()` 返回当前事件实例与选择记录的引用；重复选择返回原引用，记录写入失败时选择记录 ID 可以为空。回调将这两个值明确传给 `NoteRuntime.before_event()`，音符账本不读取采集器内部的事件字典。

奖励来源仍由采集器按现有菜单、点击和首个奖励页证据归属。潜能适配器只将事件来源 ID 传给 `NoteRuntime.complete_potential_reward_inventory()`；是否与账本里待完成的单个事件同源、是否需要补读，由音符运行时判断。已有混合区间、核心/升级/商店明确来源和记录关闭路径均沿用原规则。只有真实背包导航后才重新确认潜能页，不因为参数传递方式改变而增加截图或 OCR。

金币读取以随界面移动的钱包图标定位，避免把展开的音符栏数字当余额；如果 OCR 没提供字框，会先用同帧轮廓定位文字区域，再由 OCR 确认金额。定位框本身不是金额证据。只有同一画面、相互一致的读数才能用于决策；不同读数冲突时不以重试覆盖。候选卡名也只在单次 OCR 内拼接换行，多次读取需要一致才确认身份。

主要文件：`agent_callbacks.py`、`events.py`、`event_reader.py`、`event_mapping.py`、`event_policy.py`、`value_model.py`、`observation.py`、`note_runtime.py`、`note_bag.py`。事件菜单及钱包识别配置位于 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json`、`climb_tower_neural_numbers.json`。

### 7. 商店：将可见货架转换为模型动作

商品名称与普通爬塔共用 [item_translations.json](../../../agent/custom/climb_tower/climb_tower_shop/item_translations.json)。更新译名或补充 OCR 别名时，在对应商品和区服的列表中维护；第一项用作显示名，列表中的名称都可参与识别。

`星塔_节点_商店_商店主流程_agent` 调用 `stella_value_shop`（`Shop`）。进入后先确认商店主页面、商店类型和强化费用，再逐格读取商品名、数量、实付价和专属角色信息，并读取钱包、剩余刷新次数及刷新费用。扫描和购买共用价格识别，只保留深蓝色实付价及余额不足时的红色实付价，避开浅色划线原价。即使当前买不起，也要读出商品价格，以还原完整货架。缺读时只补齐缺项，整架确认后才生成候选动作。

候选动作包括已确认可买的潜能饮品、符合当前费用的强化、仍有次数且付得起的刷新，以及离店。普通物品不会被错当成模型训练过的购买动作；商店适配器只把可映射的潜能饮品转换为模型支持的购买动作。模型根据从开局累计的路线、已有潜能、库存和金币估算动作收益，不把“进入商店”当成全新开局：首家商店货架完整读出后清除初始标记；最后一层商店内仍处于路线推进阶段（`ADVANCE`），只有离店且路线结束后才转为终局（`END`）。当前冻结的 M213 策略评估潜能饮品、潜能强化等对普通潜能目标的影响，不购买音符。

`potential_adapter.prepare_actions()` 返回 `PreparedActions`，显式包含投影后的 `state`、合法 `actions` 和模型动作到可见商品格的 `action_slots`。调用方分别应用状态、选择动作和定位格位；适配器不再把这些结果回写到输入的决策快照。同类型、同价饮品仍合并为模型动作，并保留首个可执行候选格，指定角色饮品与普通饮品分别计数。运行时生成决策快照时保留深拷贝，后续 UI 数据变化不会改写这次决策输入。

动作由原 Pipeline 商店子节点执行，神经网络商店逻辑负责决定动作并监督结果。刷新须看到刷新次数减少或确认实际扣费，并读到完整且稳定的新货架；强化后重新确认强化费用和钱包；购买后则等待潜能奖励页，并用商品、奖励和钱包证据关联到本次购买。只有奖励与操作能对应上，才把饮品库存和潜能来源写入模型状态。页面导航或动作结果不能确认时停止，不能把“点击成功”当成交易成功。

`RunSession.purchase_wallet_capture()` 保存购买前的钱包，`purchase_evidence.py` 用同一 `operation_id` 下首个完整的后续钱包计算扣款。奖励页内刷新另有操作编号，这样不会把刷新费算进商品价格。购买记录从采集到导出均分别保留 `pipeline_succeeded`（购买子任务返回成功）、`reward_committed`（确认饮品奖励页并更新货架库存）和 `debit_confirmed`（钱包差额等于实付价，缺读时为未知）。`success` 表示前两项均成立。饮品奖励页后续领取失败时，货架可能已经扣掉一件饮品，因此要分别记录子任务和奖励的结果。

完整饮品奖励页在 `ObservationTracker.open_page()` 的既有位置核对购买来源，并仅在尚未提交时更新库存及购买标记。`potential_adapter.consume_drink_stock()` 只按饮品类型和价格返回扣除一份库存后的模型状态，不接收或修改 Item、purchase。调用点在转换成功后设置 `item.bought` 与 `purchase.committed`；来源不符或库存不足不提交。后续奖励刷新不会再次扣饮品库存，真实潜能持有仍在确认拿走后更新，两个时点不能合并。

### 商店嵌套领取失败的证据顺序

商店操作通过 `SamplingCollector.defer_finish()` 延后归档。领取回调仍立即停止任务，外层购买和强化先写入操作结果，再结束本局。否则内层清空采集状态会丢失已确认的钱包扣款。购买分别记录 `pipeline_succeeded`、`reward_committed` 和钱包扣款。强化用首次关联的钱包读数 `coins_after` 核对费用，操作结束余额 `coin_after` 取管线最后一次钱包观测，可能包含奖励页刷新费。领取失败时商店缓存仍是旧值，结束余额缺读时留空。

完整候选页的统计资格由 `research_schema.sql` 的 `potential_draw_validity` 决定。只有 `origin_operation_id` 与失败操作相同的商店奖励页，才免受该操作的 `unconfirmed_action_tail` 或 `action_not_confirmed` 影响。候选自身的识别冲突、持有历史不完整以及其他操作的质量问题仍按原规则排除。

Maa 5.16.1 的嵌套 Pipeline 收到停止请求也可能返回成功。`pipeline_succeeded` 保留这个返回值。拿走回调确认页面已切换并提交领取时，采集器立即记录领取结果。只有领取记录属于本次强化，`operation_confirmed` 才为真，`confirmation_record_id` 指向该记录。这样即使领取后立即停止也能保留确认。付费强化的 `debit_confirmed` 单独由钱包差额决定，免费强化保持未知。购买或强化抛异常时先记录结果再继续抛出，Pipeline 未返回则保留未知。

真实货架始终由 `ShopContext.items` 保存：普通补读复用已有 Item 并只补缺项，成功刷新重建商品，不由采集器恢复 `bought/checked`。`ObservedShopHandler._record_stock()` 维护研究记录用的访问、代次和签名；`collector.stock_scan_id` 仅供购买及其他研究事件关联，不是另一份模型库存。确认刷新即建立新代，同代且记录内容相同才复用扫描 ID；刷新后商品完全相同也不能借用旧代的已购标记。

适配器先记录已确认货架，再由 `_complete_refresh_record()` 消费并清空待补齐的刷新记录。后者只按原公式整理日志：钱包必须属于最终货架采样窗口，扣费、货架完整性和次数/变化证据决定日志的确认质量。原 UI 的刷新返回值另行保留，日志缺证不会将 UI 成功改成失败；不能为统一两者而追加 OCR、重读货架或改用更早的完整钱包。

主要文件：`agent_callbacks.py`、`shop.py`、`shop_ui/context.py`、`shop_ui/handler.py`、`shop_ui/interactor.py`、`shop_ui/price.py`、`shop_ui/purchase.py`、`purchase_evidence.py`、`potential_adapter.py`、`value_model.py`、`observation.py`、`tower_sampling_collector.py`。商店节点与页面导航在 `assets/resource/base/pipeline/climb_tower/climb_tower_agent_sub_shop.json`，实付价的颜色范围在同目录的 `climb_tower_neural_numbers.json`。

### 8. 结算：读取成绩、潜能数量和音符结果

`星塔_记录界面_读取数值_agent` 将原来的单一保存记录识别扩展为两种条件：原保存文字节点或神经网络专用结算图形。扩展图形识别是为结算按钮文字不可读时保留进入结算读取的机会；随后 `SettlementReader` 再等待结算页面和数据稳定，读取纪录等级及三名角色的潜能数量。潜能数量要先定位三个 UI 数字锚点，再分别进行 OCR 和冲突检查；锚点缺失、读数冲突或与已知字段不一致时将相应值留空，不用部分数字拼出看似完整的总数。

确认后的等级和潜能总数写入原循环节点的 `attach`，以保持原 Pipeline 的结算交接方式。若本地记录未启用或本局尚未确认开始，回调直接委托原有 `RecordScanAction`，避免神经网络采样逻辑改变普通结算行为。记录开启时，读取完成后还会定位结算页的音符标签，点击进入音符结算页并采集最终库存；如果标签或页面转换不能确认，保留缺失状态，不把潜能结算结果当成音符库存。

主要文件：`agent_callbacks.py`、`settlement_reader.py`、`agent/custom/climb_tower/climb_tower_record_scan.py`、`settlement_counts.py`、`note_runtime.py`、`tower_sampling_collector.py`；结算保存图形节点位于 `assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`。

### 9. 结果页与音符变化：读取后继续

`星塔_点击空白处关闭_agent` 的动作由 `stella_note_continue`（`NoteContinue`）接管；覆盖还加了一个短暂的界面稳定等待。等待到期只代表应重新观察，并不直接报错或点击。回调重新捕获结果画面，读取音符库存条，并在页面允许时读取楼层。原因是事件奖励页、战斗奖励页和潜能页都可能连续出现，单看“页面出现了”不足以判断音符增量属于哪种来源。

`NoteRuntime` 将快照和待确认来源关联：战斗奖励、事件奖励、连续事件或两者合并的区间分别处理；若一个奖励页无法确认楼层或来源，就不把这段增量强行归给某一场战斗。事件消费音符时，账本先要求操作前库存作为基线，操作确认后再读取后续库存；如果来源只能确定为一个区间，就记录区间而不是伪造单个事件/战斗的精确增量。未知钱包或楼层保持空值。页面采集期间若重新导航，原始继续按钮坐标失效，回调必须在返回页重新识别按钮后再点击；否则使用本帧确认的按钮框。最终等待仍交给框架超时诊断。

楼层读取和音符数字采集按各自需要执行。关闭研究记录时，仍用 `note_ocr.locate_inventory_bar()` 定位清晰库存条，确认页面依据后读取模型需要的楼层；不读取音符数字，也不为此开启背包或创建音符账本。“点击继续”节点也能命中其他关闭页，因此没有库存条时直接继续，不等待不存在的楼层。发生重读时，每帧重新确认继续按钮并更新点击框。

每次楼层观察先更新 `RunSession`，再尝试记录。`current_floor_observation` 保存本次读数，包括缺读、冲突和页面遮挡；`last_confirmed_floor` 只由完整的 `floor_hud` 实读更新，供 `ObservationTracker` 约束路线下界或恢复位置。潜能页、事件页的遮挡和外部提供的楼层不能覆盖这份清晰 HUD 锚点，也不能把历史锚点伪装成当前页面的精确观察。采集器保留的楼层缓存仅关联已经写下的研究记录 ID，不能再作为模型事实来源。

楼层 OCR 的候选先验同样使用会话中的清晰 HUD 锚点，以及 Tracker 已确认事件的路线候选；音符账本的 `floor`、pending 与 revision 只参与奖励归因，不控制模型读楼层时的候选。商店范围仍由每次进出商店都更新的页面模式限定。尚无清晰 HUD 且 Tracker 尚未建立时，两种记录设置都不预填楼层。原 OCR 阈值、裁剪及共识算法保持，实际提前结束由这些统一的运行先验决定。

楼层记录成功或语义去重后，记录器实际返回的行 ID 附到同一次会话观察的 `floor_observation_id`；当前观察和历史锚点因此能准确关联原始记录。写入失败或关闭记录时，楼层事实仍有效，记录引用可为空。事件归因直接沿用观察自身的引用，不能按相同楼层数字借用另一条记录；路线恢复日志兼容既有 `record_id` 输入。

主要文件：`agent_callbacks.py`、`session.py`、`note_runtime.py`、`note_ledger.py`、`note_ocr.py`、`note_floor.py`、`observation.py`、`ui_flow.py`、`interactor.py`。

### 10. 对局循环：清理边界并控制重复次数

`星塔_循环用节点_agent` 使用 `stella_value_loop`（`TowerLoop`）。每次进入先结束音符账本的本轮边界，并通知采集器归档已结算对局，或将没有结算确认的记录标记为未完成；然后清除本轮会话、潜能追踪器、待领取选择、刷新状态和事件缓存，避免下一局继承上一局状态。目标预设和已加载模型可以保留在任务运行时中。

循环次数来自选项 `神经网络爬塔_爬塔次数` 写入的 `attach.loop_count`。回调把剩余次数减一：还有剩余时更新节点数据并禁用返回主页节点，让原 Pipeline 按既有后继进入下一轮；没有剩余时重新启用返回主页节点，让任务按原流程结束。此逻辑以用户设定次数为准，不依赖结算 OCR 的成功与否；结算识别失败会影响可用记录数据，但不会偷偷改变循环次数。

主要文件：`agent_callbacks.py`、`maa_hook.py`、`note_runtime.py`、`sampling_data.py`；循环节点及其原有后继关系定义在 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json`。

### 11. 回调共享的运行与记录设施

上述回调由 `agent/custom/__init__.py` 接入 Agent 导入链。`climb_tower_neural/__init__.py` 先注册轻量回调，首次执行回调且权重可用时才加载神经网络运行时。标准爬塔实现集中在 `agent/custom/climb_tower/`，由神经网络模块复用。`maa_hook.py` 维护任务模式、模型和每局追踪器，供潜能、事件及商店共享目标、持有、金币与路线状态。

`image_ops.py` 使用 NumPy 预处理 MaaFramework 返回的 BGR 截图。背包使用首列图像的归一化相关性恢复垂直滚动距离，音符与楼层读取使用局部裁剪、颜色掩码和缩放辅助原有 OCR。音符图标匹配仅重采样搜索区域，采样位置、图像尺寸和识别框坐标沿用整帧缩放。色相阈值沿用 0–179 刻度，连通域使用 8 邻接。修改这些算子时应使用同一组截图对照滚动位移、卡名和数字读数。

`interactor.py` 与 `ui_flow.py` 通过 Pipeline 统一调度截图、重读和超时；`pages.py` 识别页面类型；`ocr_number.py` 校验数字读数。`session.py` 承接开局确认、本次楼层观察、历史 HUD 锚点和当前钱包，并维护可跨 Maa 嵌套回调线程的操作关联。开启本地记录时，`tower_sampling_collector.py` 的潜能、商店适配器将识别与操作连到 `sampling_data.py`、`sampling_events.py` 和研究数据库模块；识别记录代理 `SamplingContext` 与 `SamplingCollector` 同在 `sampling_data.py`，采集器不再为创建这个代理反向导入 UI 适配器。是否上传由任务选项控制，上传实现位于 `sample_upload.py`。这些是多个节点共同依赖的基础设施，不是额外的主流程节点。

潜能选择、刷新和商店强化的执行包装集中在现有 UI 适配模块的 `run_observed_operation()`，采集器不负责调用处理器动作。该包装始终在会话中建立操作作用域；关闭记录时直接调用原动作，开启时额外记录操作前后状态。商店刷新关闭记录时也建立独立操作 ID，但仍使用原来的无采样帧包装路径，不增加 UI 读取。

潜能记录入口 `SamplingCollector.prepare_offer(data)`、`observe_offer(data, read)` 直接接收已读取的页面数据，适配器不把可执行 handler 交给记录器。奖励链、页指纹和计数、研究库存审计、楼层记录引用及去重仍由采集器维护；名称与槽位的证据关联沿用原逻辑，不能因只移动函数位置而改变 OCR 记录含义。`ObservedInventory` 是独立的研究投影，不替代模型的已确认持有。

钱包只有一条解析路径：`Interactor` 沿既有节点、定位、阈值和重读顺序取得金额，在原返回位置通过 `on_wallet` 发布最终值与质量；价格和等级读取不发布钱包。`maa_hook.py` 的 `observe_wallet()` 先更新会话，再交给采集器记录。`current_wallet_observation` 表示当前读数，缺读、非法数字和冲突也会替换旧值；事件钱包图标缺失同样发布缺读。零余额是完整金额，不用历史成功读数补齐缺失。

`SamplingCollector.record_recognition()` 只保留本次采样窗口内的原始识别及定位关联，不再重新解析钱包。`record_wallet()` 消费上述最终观察；会话生成的 `observation_id` 同时用作该钱包日志行的 `record_id`，原始识别 ID 只留在记录侧。每次逻辑读取产生一条最终钱包观察，相同金额的再次读取也有自己的 ID；这与 OCR 尝试次数无关。购买前的观察 ID 显式写入 `purchase_attempt`，导出时按该引用还原，不能把缺失金额补成更早的完整余额；未含此字段的旧日志仍按旧规则导出。记录写入失败沿用日志缺口处理，不撤回会话已收到的钱包观察。

`emit()` 的可选 `record_id` 参数表示日志行身份，不属于会被压缩过滤的游戏语义字段。潜能领取确认也使用这个入口：先交给 `ObservedInventory.confirm()` 的 ID 必须与实际领取确认记录一致，终局库存的 `confirmation_record_id` 才能在数据库导出中找到对应来源。

## 状态记录、日志与维护约束

模型及业务范围是冻结配置，不应从界面逻辑推断为“自动学会所有策略”：M213 当前按普通潜能终局收益评估潜能选择、可行刷新和潜能饮品/强化，不购买音符；事件使用事件概率与后续潜能价值单独估值，答题使用官方答案规则。预设日志按背包实际标记的目标等级求和，列出三名角色各自的目标及全队合计。候选行的“预期”是所选动作后的终局估值，变化行相对于上一次预期；第一次决策则以开局估值为基准。这些值不是保证达成的收益，也不是战斗胜率。

音符来源归因和研究质量检查通过 `critic/rules.py` 读取当前策略的路线、战斗楼层与末层。该视图从冻结模拟器的同一份 `ROUTE` 派生数据，记录模块不再解析 Python 源码，也不另抄一份路线。它只统一当前 M213 的规则来源；新难度涉及层数、机制或模型输入变化时，应按新的训练契约更新对应策略，不能单改视图就宣称旧权重已经适配。

实机侧的普通潜能等级上限和商店刷新上限也由 `critic/rules.py` 统一提供，供背包读取、潜能领取、货架确认和采样共用。强化费用取模型的 `PRICES`，饮品库存维度取 `EMPTY_STOCK`。更换难度涉及这些数值时，应同时核对模拟器与新模型的输入和动作定义。

目录和观测必须严格区分。用于估值的池顺序可以基于潜能目录补全，但需标记为推导/估值信息，不能写成游戏实读池位；钱包或楼层没有可靠证据时留空。批量识别楼层、音符图标或结算协奏卡片时，各轮都检查任务是否停止；中途停止应保留已确认的内容，同时让本轮结算或楼层观测保持不完整。

本地研究数据库只保留推导爬塔状态所需的预设、游戏观测、实际操作、结算和质量标记，不保存截图、逐帧 OCR 或模型估值；对局进行时写临时日志，结算、中断或恢复时才归档。每局使用独立编号，不生成个人或安装标识。数据库 `research.sqlite3` 的四张表为 `presets`、`runs`、`records`、`quality_issues`。归档和恢复以对局为单位避免重复写入；同一对局只由一个 Agent 恢复，写库失败时在后续任务或对局边界重试。

每次展示潜能时记录抽取前持有历史的完整性，供抽取统计筛选。潜能池快照由展示和领取历史推导，继承当时的持有质量。开局供给与首战后库存之间缺少独立读数，两次奖励的合计变化标为 `opening_included=true`，单场战斗掉落统计从后续独立区间开始。

池位可以采用最可能的本地槽位。快照用 `position_identity_inferred` 标出仍依赖推测的位置，归档保留其重建来源。只要其他质量检查通过，这条快照仍为有效。一次推测抽取会影响本次交换可能涉及的位置，后续清晰读数能逐步确认这些位置。

零目标卡按角色、品质和等级合并计数。若早先的领取因身份存疑而未入账，后续确认升级时只扣已有的旧等级数量，并记录新等级；已有的历史缺项继续保留。

`sampling_evidence.ObservedInventory.confirm()` 仅将已确认身份纳入完整持有历史：页面跳转只能证明领取发生，不能验证名称模糊匹配；库外槽位的估计绑定以 `identity_inferred=true` 记录，领取后研究持有历史仍标为不完整，不能因模型继续运行或下一轮等级吻合而改成已知事实。通过名称证据验证的模糊匹配仍按已确认身份处理；运行时估计与研究记录的严格确认分别保留。

已持有的潜能若经历一次身份存疑的领取，原先确认的等级只能作下限。只读到队友卡名前缀或只能推测库外槽位时，采样保留候选 ID，用它们定位可能升级的卡。下次读清这张卡时，用卡面等级恢复后续核对，先前的领取仍保留为历史缺口。

「分享数据，帮助改进模型」默认关闭，且与本地记录分开授权。开启后，结算或中断时将已归档的本局记录通过 `POST https://35.213.73.34/v3/runs` 上传，无需 Token；收尾最多等待 5 秒，未收到回执的授权对局留待之后重试，各局互不阻塞。公开 v3 接收端沿用原 ZIP 信封，`research_wire.py` 标记内容版本；信封里额外的四个旧表名仅为空数组。

发行数据统一放在模块的 `data/` 下，Python 通过 `paths.data_path()` 定位，不依赖调用者所在文件夹。已有模块根参数仍作为根使用：运行时的 `root`、上传器的 `module_root` 都指向 `climb_tower_neural/`，不是 `data/`。维护位置如下：

| 内容 | 模块内路径 |
| --- | --- |
| 功能开关 | `data/config.json` |
| 游戏区服语种、别名与目录名称字段 | `data/locales.json` |
| 角色、潜能与已知池序 | `data/character_name_catalog.json`、`data/potential_name_catalog.json`、`data/pool_orders.json` |
| 背包、潜能、音符 OCR 规则 | `data/bag_preset_rules.json`、`data/potential_ocr_rules.json`、`data/note_ocr_rules.json` |
| 事件映射与音符规则 | `data/event_rules.json`、`data/note_rules.json` |
| 上传默认设置 | `data/upload_settings.json` |
| Agent 注册绑定、模型清单 | 根目录 `agent_bindings.json`、`model.json` |

`data/` 只存发行数据。应用本地上传覆盖仍为 `config/neural_network/research_upload.json`，采集设置仍为 `agent/agent_config/tower_sampling.json`；这些可写设置不能移入发行规则目录。Pipeline、图片、Agent i18n 继续按项目原结构维护。

`language.py` 统一解析 `data/locales.json`。当前配置只有 `cn`、`jp`，分别接受 `zh_cn`、`ja_jp` 别名；预设编译、池序匹配、模型身份和研究记录使用同一目录名称字段。游戏语种仍来自资源节点的 `attach.lang_type`，事件读取保留当前事件节点的来源，不读取客户端 UI 语言。任务准备阶段按配置中的支持列表判断语种；预设缺失语种时保留既有日语名称字段默认行为，不据此放行未知区服。后续新增区服应同时维护该映射、名称目录和对应 Pipeline/OCR 资源，并完成相应区服验证。

`locales.json` 的 `catalog_name_alias_fields` 是目录名称别名元信息，不是支持区服条目。`catalog_name_fields()` 合并它与各语种的 `catalog_name_field`，供完整预设目标、模型/研究名称索引及目录展开工具共用；增加名称字段无需逐个修改 Python 白名单。研究压缩也使用同一字段集合：已知 ID 的条目省略冗余名称，未知或本地身份保留名称。该元信息保留原有中、日、英、繁体名称别名顺序，正式支持语种仍为 `cn`、`jp`。

更新潜能目录时，用 `python tools/catalogs/tower_catalog.py expand agent/custom/climb_tower_neural/data tmp/tower-catalog` 展开维护目录，更新完成后运行 `python tools/catalogs/tower_catalog.py compact tmp/tower-catalog` 生成发行目录；默认输出已经指向模块的 `data/`。发行版按潜能 ID 存储，保留中日名称及来源。

M213 权重及移入的推理、模拟代码由 dango636 按本项目的 [MIT 许可](../../../LICENSE)分发。更换模型时同步更新 [model.json](../../../agent/custom/climb_tower_neural/model.json) 中的权重路径、摘要和来源。

## 平台接入与后续维护

当前神经网络爬塔仅支持 Windows x64。任务声明、Agent 代码、Pipeline 与图片资源随各平台发行，模型权重随 Windows x64 包发行。

### 当前接入点

- `agent/main.py` 导入 `custom`，由 `agent/custom/__init__.py` 导入标准爬塔模块并调用神经网络模块的 `register_lazy_callbacks()` 注册轻量回调。无需独立入口或对 `main.py` 做平台分支。
- `model.json` 声明的权重被发行包省略时，神经网络注册异常不会阻断普通 Agent。模型已随包发行时，注册异常直接报告。
- 首次执行回调时检查 `model.json` 指向的权重。缺少权重时记录运行环境提示并终止回调。模型配置错误交给运行时报告。
- `tools/ci/download_deps.py` 和发行工作流使用 `assets/requirements-win-x64.txt` 准备 Windows x64 的运行依赖。神经网络模块使用 NumPy，MaaFramework 的 Python 绑定也依赖 NumPy。
- `tools/ci/package_common.py` 的 `copy_agent_files()` 在不包含模型的发行目标中读取神经网络目录的 `model.json`，并排除其中 `checkpoint` 指向的文件。更换或移动权重时，以 `model.json` 为路径来源，不要另加硬编码路径；该打包行为有专属测试覆盖。MFA 和 Android 暂存流程按目标平台设置是否包含模型；MXU 是 Windows x64 包，保留权重。其他 Agent 文件及神经网络任务、Pipeline、图片都按通用流程复制。
- `install.yml` 在归档后使用发行 Python 导入神经网络运行时、回调和背包读取器，并加载随包模型。`tools/checks/tower_neural_tests/` 下的单元测试由 `.github/workflows/check-tower-neural.yml` 独立运行。

### 扩展平台时

1. 验证目标平台的 NumPy、Agent 运行环境及模型推理能力。
2. 在对应发行暂存流程中允许复制 `model.json` 指定的权重。平台行为只需调整 `copy_agent_files()` 的 `include_neural_model` 参数，不要删除任务、Agent 模块或资源文件，也不要改写标准 Agent 入口。
3. 扩展 `.github/workflows/check-tower-neural.yml` 的测试平台，并使用对应发行 Python 验证运行时可导入、回调能用随包权重启动模型。
4. 同步更新[项目结构](../项目结构.md)的平台支持范围、依赖清单和模型打包说明。

### 解除平台限制时

本节只说明如何移除临时的平台容量限制；神经网络爬塔任务、资源、Agent 回调及测试继续保留。是否移除该功能由维护者另行决定。

各目标平台均完成上述验证后，可统一复制模型权重，并移除 `copy_agent_files()` 的 `include_neural_model` 选项及相关裁剪逻辑。同步更新[项目结构](../项目结构.md)中的平台、依赖、权重及发行验证说明。

## 建议优化

本节是维护者对贡献者的建议：
- 后续改动建议顺便将文件架构定好，方便后续精简代码逻辑。如果能做到后续只用修改固定位置的json文件、神经网络文件就能对新难度或其他服务器的文本适配，而不需要修改其他代码，那就最好了。
