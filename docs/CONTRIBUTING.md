# 参与 MaaStellaSora 贡献

《星塔旅人》作为一款小体量游戏，社区开发力量非常宝贵。目前星塔助手已经完成了基础功能，但面对更多样的日常与活动需求，单靠少数开发者的力量仍然有限。

无论你是提报运行中的 Bug，还是参与代码贡献，我们都非常欢迎！在动手前，推荐先阅读 [项目结构](zh_cn/项目结构.md)、[Pipeline 编写规范](zh_cn/Pipeline编写规范.md) 与 [Custom 函数编写规范](zh_cn/custom函数编写规范.md)。

---

## 提交 Issue

如果你暂时没有时间编写代码，或者在运行中遇到了难以解决的异常，提交 Issue 是对项目极大的支持：

1. **Bug 反馈**：
   - 提交前请先在已有 Issue / PR 中搜索，避免重复反馈。
   - 请使用 [Bug 反馈模板](../.github/ISSUE_TEMPLATE/cn-bug-report.yaml)，如实填写助手版本、所在区服、控制器类型、任务选项及发生时间。
2. **调试截图与日志提取**：
   - **运行截图**：左下角齿轮「设置」→「运行设置」→ 开启「保存截图」与「显示命中截图」。截图保存在 `debug/vision` 目录。对于识别问题，建议提供原始分辨率的游戏截图，复现完成后请记得关闭该选项以防持续占用磁盘空间。
   - **运行日志**：三种日志均在运行时自动记录，复现后请将对应日志打包上传并注明发生时间：
     - `logs` 文件夹：保存 MFAAvalonia 客户端界面运行日志；
     - `debug` 文件夹：保存 MaaFramework 核心运行与识别日志（`maa.log` 及存在的 `maa.bak.log`）；
     - `debug/agent` 文件夹：保存 Agent（Custom Action / 自定义策略等）的运行日志，以日期命名（如 `debug/agent/YYYY-MM-DD.log`）。涉及爬塔策略、战斗逻辑等 Agent 自定义流程问题时请务必附带。
3. **功能构想与大改动探讨**：
   - 如果你计划实现一个大型新功能或重构核心模块，强烈建议先提交 Issue 说明构想，或者直接向当前活跃的维护者打声招呼，确认需求方向，避免重复劳动或设计偏离。

## 提交 Pull Request (PR)

### 1. 架构选择：扩展现有模块还是新增模块？

在动手编写功能时，是修改原模块还是新建模块，主要取决于**业务流程的重复度**：
- **流程高度重叠**：如果新功能与已有模块在界面流转、前置逻辑上有较大重叠（如共用主界面跳转、前置状态检查等），应尽量在原模块上扩展，保证逻辑内聚。
- **流程相对独立**：如果界面路径、操作逻辑与现有模块无明显关联，建议建立独立的新模块。
- **人工决策与例外处理**：
  - 流程设计和模块边界 AI 通常难以准确权衡，请**以人工判断为主**，摸不准时随时与维护者沟通讨论。
  - **高收益大改动特例**：如果你实现了一个对原有功能提升极大、但因改动过于复杂而难以直接合并的代码，**可以先在不动原模块代码的情况下，通过独立文件做成独立模块提交**（或先提 Draft PR）。只要实机验证可用，后续维护者会协助将其平滑整合。

### 2. PR 质量审查维度

维护者在审阅 PR 时，会按照从「功能正确」到「代码优雅」的层级综合评估代码质量：
1. **逻辑正确与场景还原（最优先）**：代码逻辑必须严格符合游戏的实际交互流转与游戏机制，没有逻辑漏洞，杜绝死锁与流程跑偏。
2. **极端边界与异常容错**：充分考虑网络延迟、突发弹窗打断、加载动画超时等极端边界情况，确保在非理想状态下具备容错重试或安全退出机制。
3. **低侵入与模块隔离**：改动需具备良好的内聚性，严禁产生未隔离的全局变量，避免对其他不相关模块造成状态污染或隐式耦合。
4. **结构规范与合理归类**：按照功能职责将代码放在该放的文件和目录中，命名与组织风格符合项目现有规范。
5. **优先使用框架特性与实现精炼**：优先利用 MaaFramework 原生提供的算子与机制实现需求，避免重复造轮子或编写死循环，保持代码简洁、无多余冗余逻辑。

### 3. 代码审查与准入原则

维护者审阅 PR 时的核心原则是评估 **「功能收益」是否显著大于「后续维护成本」**：

- **全新模块（从 0 到 1）—— 能用即可，鼓励填补空白**：
  - 新建模块从无到有，填补了功能空白，因而准入门槛较为宽松。**只要实机能稳定跑通、不影响其他模块，提 PR 大概率会被采纳**。后续代码细节大家再共同迭代优化。
- **现有模块修改（从 1 到 N）—— 慎防劣化，要求正向收益**：
  - 已有模块承载了用户的日常使用，任何改动都会基于上述 5 项质量标准对比前后实现。
  - 修改必须带来明确的**正向提升**（如大幅提升稳定性、优化执行效率、修复确凿的逻辑缺陷等）；如果改动带来了过高的理解成本或破坏了原有架构的整洁度，维护者将倾向于保持现状。

### 4. 关于 AI 辅助开发的慎重说明

我们理解并认可 AI 是极佳的辅助工具，但 **AI 不应成为将维护负担转嫁给项目的理由**。结合上述的准入原则，请大家在利用 AI 时注意以下边界：

1. **实机验证是一切的前提**：
   严禁未经任何实机运行、直接复制粘贴 AI 生成的代码提交 PR。无论是新模块还是旧模块，**必须附带你在真机/模拟器上的测试结果（截图、日志或录屏）**。
2. **修改现有模块：请贡献者自行把控质量**：
   对于已有成熟模块的修改，**不接受**未经人工理解与梳理、全凭 AI 生成的碎片化改动，更无法由维护者代为清理重构。请务必自己读懂代码，确保修改符合项目的架构规范与质量要求。
3. **实现全新功能：代码粗糙可以接力，但请「先沟通」**：
   如果你通过 AI 探索并跑通了一个全新的游戏功能，但由于缺乏架构经验，写出来的代码存在兼容性隐患、或者不知道如何规范化：
   - **请先通过 Issue 或交流渠道沟通**：贡献者往往难以判断某个需求是否属于大众刚需。先确认维护者与社区是否认可该功能的方向。
   - **确认有价值后，放心提交原型**：如果确认是大家期望的功能，你完全可以采用独立文件形式或提交 **Draft PR**，并注明“核心流程已跑通，需要架构整理协助”。此时维护者会非常乐意接力，协助你将代码打磨合入。

### 5. 提交规范

1. Fork 本仓库，从 `main` 分支拉出特性分支开发；目标分支统一为 `main`。
2. 编码与资源组织请遵循 [Pipeline 编写规范](zh_cn/Pipeline编写规范.md) 与 [Custom 函数编写规范](zh_cn/custom函数编写规范.md)。
3. 提交信息建议使用标准语义化格式：`<type>(<scope>): <简练中文描述>`，例如 `fix(pipeline): 修正邀约页面识别区域`。
4. PR 描述中写清解决的问题、主要改动、关联的 Issue，以及实机测试的环境与结果。

### 6. 我们可能会婉拒的 PR（合规与安全底线）

星塔助手始终以“辅助日常、减轻重复负担”为定位。为维护游戏的可持续运营与健康生态，以下情况的 PR 将不会被合入：
- **破坏公平竞技**：包含可能严重打击 PVP、排行榜玩家积极性、破坏公平竞争环境的功能。
- **触及商业运营底线**：包含批量刷初始号获利、尝试规避正常体力与资源消耗机制等破坏二游可持续运营环境的功能。
- **高危封号风险**：超出正常辅助范畴、模拟极限非人操作等可能导致官方安全封禁的高风险功能。
