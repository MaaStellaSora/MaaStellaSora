# 参与 MaaStellaSora 贡献

星塔旅人作为一款小体量的游戏，能吸引到的开发人员相当有限，所幸经过磕磕碰碰，终于把**基础功能**都完成了。
但是，面对各种用户不同的需求，星塔助手能做到的仍然有限，所以我们非常欢迎各种形式的贡献。

[项目结构](zh_cn/项目结构.md)介绍源码目录、资源加载方式、开发工具和发行包布局。

编写或修改 Pipeline 时，请遵循 [Pipeline 编写规范](zh_cn/Pipeline编写规范.md)，统一节点字段、参数层级和覆盖写法，并完成对应验证。

## 贡献方式

作为一款长期人手不足的项目，我们对贡献的方式非常宽容，但是为了保证项目能够长期维护，我们还是希望贡献者能先阅读以下内容：

### Bug 修复

- Bug 修复是最重要的贡献之一。即使你不懂编程，或者暂时没有时间写代码，也可以通过**提交 Issue** 帮助我们发现问题；提交前先搜索已有 Issue 和 PR，看看是否已有修复或讨论。
- 如果你非常清楚问题的原因，可以用**简短的文字**说明复现步骤、预期与实际结果，并指出相关代码或节点。
- 如果你不确定问题出在哪里，可以按下方步骤记录运行过程，通过 [Bug 反馈模板](../.github/ISSUE_TEMPLATE/cn-bug-report.yaml)附上截图及日志。同时说明助手版本、区服、控制器、任务选项和问题出现的大致时间，方便定位。
- 如果你有能力修复 Bug，可以直接**提交 PR**，说明问题原因、修复方式和验证结果。

#### 调试截图与日志

以下操作基于 MFAAvalonia，路径相对于软件运行目录。

1. 运行截图
   - 通过左下角的齿轮图标 → 选项 → 运行设置，开启“启用保存截图（用于调试）”和“显示节点命中截图（用于调试）”。
   - 截图保存在 `debug/vision` 文件夹中。可以浏览内容，只上传问题出现前后相关节点的截图。
   - 对于识别问题，同时提供模拟器或控制器截取的游戏原图，保留原始分辨率，便于复现识别过程。
   - 记录完成后关闭上述选项，避免持续截图占用磁盘空间、拖慢运行速度。
2. 日志文件
   - `logs` 文件夹保存 MFAAvalonia 的运行日志，`debug` 文件夹保存 MaaFramework 的运行日志。
   - 两种日志均会在运行时自动记录，无需额外开启截图选项。
   - 复现问题后关闭客户端，再上传 `debug` 中的 `maa.log` 和存在的 `maa.bak.log`；客户端启动或界面问题同时附上 `logs` 中对应时段的日志。
   - 日志上传完整文件，并说明问题发生的时间点；体积较大时可以压缩后上传。

### 新模块开发

- 如果你想对全新的游戏模块进行功能开发，欢迎在保留现有模块功能的基础上实现，并在 PR 中说明操作流程、任务选项和实机运行结果。
- 在开发之前，我们强烈建议你**先提交 Issue 或草稿 PR 说明计划**，或者**直接向当前活跃的开发者打声招呼**，避免重复开发。

### 对现有模块进行功能追加

- 爬塔之外的模块代码量较小，可以在**理解现有流程与调用关系的基础上**追加功能，并验证受影响的原有功能。
- 爬塔模块代码量较大，追加功能时需要兼顾后续维护；请先与维护者讨论方案，再按模块职责进行修改。

### 代码重构

- 重构需要先了解相关的 MaaFramework 接口与项目实现，说明当前问题、调整范围和预期收益。
- 我们强烈建议你先与维护者讨论方向，再将修改拆成可独立审查和回退的提交，并验证受影响的流程。

### 不同服务器的内容适配

- 星塔助手虽然支持不同地区服务器，但由于开发及测试人手不足，各区服的功能覆盖和验证程度可能不同。
- 如果你愿意协助提升某一区服的使用质量，可以与维护者联系，或从实际遇到的识别错误、文本差异和缺失流程入手，修改后提交 PR。
- 区服差异写入对应资源包，并核对与基础资源叠加后的效果；具体组织方式见[项目结构](zh_cn/项目结构.md#资源加载)和 [Pipeline 覆盖规范](zh_cn/Pipeline编写规范.md#区服与界面覆盖)。提交时说明实际测试的区服与控制器。

### 其他

- 对于上面没列出的贡献方式，可以先提交 Issue 或直接联系当前维护者讨论。

## 提交 PR

1. Fork 本仓库，从 `main` 创建工作分支。围绕一个问题或功能修改，准备 PR 时以本仓库的 `main` 为目标分支。
2. 按[个性化配置](zh_cn/个性化配置.md#格式化与提交检查)检查改动文件；Pipeline 修改完成[提交前验证](zh_cn/Pipeline编写规范.md#提交前验证)。涉及运行行为的修改，由贡献者进行人工审阅和实机确认。
3. 提交按可独立回退的改动组织，提交信息使用 `<type>(<scope>): <简练中文描述>`，例如 `fix(pipeline): 修正邀约页面识别区域`。
4. PR 说明写清解决的问题、主要改动、关联 Issue，以及实际验证的环境、场景和结果；未验证的范围如实说明。接口、目录或使用方式变化时，同步更新对应文档。

使用 AI 辅助开发时，由贡献者理解、审阅生成的改动，并核对实际验证结果。维护者结合代码审查、验证结果和后续维护成本决定是否合入；自动检查的覆盖范围见 [PR 自动审计](../.github/PR_AUDIT.md)。
