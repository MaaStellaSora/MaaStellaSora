# 爬塔（神经网络）

## Pipeline 构成与覆盖

神经网络爬塔复用原版爬塔的 Pipeline 作为主流程：出发、进入星塔、楼层探索、战斗和页面导航仍由原节点及其 `next` 关系驱动。任务在 `assets/interface/tasks/climb_tower_neural.json` 中声明专用入口，并通过任务级 `pipeline_override` 覆盖少数节点的识别或动作；专用 Pipeline 只补充神经网络入口、识别辅助和刷新等节点，不复制整套爬塔流程，也不修改共享的原版 Pipeline 文件。

主要覆盖点如下：

- `星塔_入口_agent` 将原准备动作替换为神经网络准备回调，并从专用入口接入原有出发流程；`星塔_跳过进入星塔流程_agent` 禁用，`星塔_星塔探索按钮_agent` 的后继改为属性塔选择，固定走主页启动路线。
- `星塔_编队角色_选择队伍_agent` 的动作改为 `DoNothing`，跳过原自动选队；`星塔_编队秘纹_agent`、`星塔_开始爬塔_检测背包按钮_agent` 和 `星塔_点击空白处关闭_agent` 分别接入音符开始、场景确认和音符继续回调，处理模型所需的状态与页面转换。
- `星塔_节点_选择潜能_agent` 改由模型识别并决策，领取节点 `星塔_节点_选择潜能_拿走_agent` 改为确认潜能领取；事件节点 `星塔_节点_进行对话选择_agent` 改用模型识别选项，并由自定义动作处理点击。
- `星塔_节点_商店_商店主流程_agent` 改由模型商店逻辑处理；`星塔_记录界面_读取数值_agent` 扩展结算页识别条件，并使用神经网络结算读取回调。
- `星塔_循环用节点_agent` 替换为神经网络循环回调，按所设爬塔次数维护对局边界；其余后继流程仍使用原节点关系。

因此，这里的“覆盖”主要是按任务替换节点行为或少量路由，不是重写爬塔主流程。普通新版爬塔任务不应用这些覆盖，继续使用原有节点逻辑。

Windows x64 原生游戏的国服、日服可从主页启动此任务，选择属性塔和爬塔次数。首次进入核心潜能页时从背包读游戏内预设；同一任务的后续对局复用目标，各局单独记录持有和库存。原有爬塔任务不受影响。

专用 Pipeline 负责导航、点击和等待；`agent/custom/action/climb_tower_neural/` 负责识别结果、推理和记录。名称、区服文字、事件和音符规则分别在目录与 Pipeline 的配置中维护。

## 节点逻辑详解

以下按一次对局的执行顺序说明任务覆盖节点。Pipeline 节点负责在合适的画面触发回调；节点名到 Agent 注册名、回调类的映射见 `agent/custom/action/climb_tower_neural/agent_bindings.json`，回调实现集中在 `agent/custom/action/climb_tower_neural/agent_callbacks.py`。除完整路径另有说明外，各节列出的 Python 模块均位于 `agent/custom/action/climb_tower_neural/`；共享的页面识别、模型状态、音符账本和记录器由各自模块承接，因此每节只列该逻辑的主要实现文件。

### 1. 从主页进入：入口和路线

专用入口 `星塔_神经网络_入口` 识别主页出发按钮后转到原版 `星塔_入口_agent`。任务覆盖把该节点的原准备动作换成 `stella_value_preparation`（`Preparation`），并将后继明确设为 `星塔_出发_agent`。原版的 `星塔_跳过进入星塔流程_agent` 被禁用，`星塔_星塔探索按钮_agent` 的后继固定指向属性塔选择，因此该任务按主页启动路线进入星塔，而不是复用原版的“已在星塔中”跳过路径。属性塔选项进一步覆盖 `星塔_属性塔选择_agent` 的图片模板，并把塔对应的两种 `active_melodies` 写入节点 `attach`；后续音符识别据此知道哪些音符属于本塔。

`Preparation` 首先确认当前确实是神经网络模式，再检查功能开关、语言和 `星塔_神经网络_运行环境` 上的 `native_windows`。通过检查后调用基类 `AscensionPreparation`，沿用原有的事件答案规则加载、潜能参数检查和可选状态重置；成功后才调用运行时开始本次任务。准备阶段因此只验证“任务是否能启动”和准备通用规则，不会读取游戏背包或加载估值模型。模型和本局追踪器延迟到第一次潜能页初始化，既避免普通 Agent 启动时承担 OpenCV/权重成本，也让神经网络任务基于实际游戏队伍建立目标。

主要文件：`assets/interface/tasks/climb_tower_neural.json`、`assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`、`agent/custom/action/climb_tower_neural/agent_bindings.json`、`agent/custom/action/climb_tower_neural/agent_callbacks.py`、`agent/custom/action/climb_tower_neural/maa_hook.py`、`agent/custom/action/climb_tower_preparation.py`。

### 2. 编队和开局：保留队伍、建立音符基线

`星塔_编队角色_选择队伍_agent` 的动作覆盖为 `DoNothing`，保留玩家当前队伍，不调用原版的自动选队函数。其余编队界面仍由原 Pipeline 导航。

`星塔_编队秘纹_agent` 使用 `stella_note_start`（`NoteStart`）。采集器启用时（配置允许且本任务的本地记录或上传选项要求采集），回调先在开始按钮仍可见时读取开局配置：塔类型来自属性塔节点的 `active_melodies`，开局音符供应和主音符从当前界面识别；无法读清的值保持未知，不以默认库存补齐。之后才点击开始按钮，并登记“已点击、等待进入”的意图。`星塔_开始爬塔_检测背包按钮_agent` 以 `stella_note_scene`（`NoteScene`）确认进入爬塔场景，运行时据此提交开局记录并创建本局音符账本、首场战斗边界。把“按钮已点击”和“已进入本局”分开，是为了避免动画、点击失败或中途退出造成幽灵对局。

账本以开局读数为基线，后续只比较同一音符在前后可靠快照中的变化；它不会把某次页面没显示的音符当成零，也不因一次局部 OCR 失败而沿用旧数值冒充新观测。若本地记录和上传采集均关闭，开始回调仍执行原点击，但不进行音符采集；上传授权与本地记录开关是不同设置。

主要文件：`agent/custom/action/climb_tower_neural/agent_callbacks.py`、`maa_hook.py`、`note_runtime.py`、`note_setup_reader.py`、`note_ocr.py`、`note_ledger.py`；识别开局状态使用的场景和交互节点在 `assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`、`climb_tower_neural_note.json` 中。

### 3. 首次潜能页：读取预设并初始化模型状态

`星塔_节点_选择潜能_agent` 的识别器覆盖为 `stella_value_potential`（`Potential`）。新任务首次到达潜能页时，运行时打开背包读取三名角色和各自的潜能目标、等级及已有数量。背包识别不只依赖标题：角色标题、卡名、品质、卡片位置和等级需符合游戏背包布局；每名角色须确认完整的 4 张核心、3 张稀有和 9 张普通潜能，目标潜能名称及等级也必须足以构造决策目录。新角色若不在现有角色目录中，则需要从背包标题及完整卡片名称建立本地识别目录；未确认的目标不会被悄悄补成已知身份。

`preset_tool.py` 把确认后的背包内容编译成模型预设：目标集合描述要追求的潜能，初始库存描述开局已经持有的潜能，两者不混为一谈。新角色标题只拼接同一次 OCR 中读取到的文字，并按组成标题的最低置信度确认；不能从不同帧拼接碎片来制造一个看似完整的角色名。之后运行时加载 `model.json` 指定的模型，建立每局独立的 `ObservationTracker`，把持有情况和潜能池身份投影到模型状态。潜能池中哪些卡还可能出现会影响未来抽取模拟；如果池中身份齐全但实际池序不可知，则保留已观察到的位置，其余按预设目录顺序构造估值所需池序。该顺序只是模型输入，不会作为“实读的游戏池位”记录。

读完背包后必须确认回到了原潜能页，才继续识别当前候选。若开包、预设编译或返回页确认失败，回调停止任务，不在未知队伍/库存上启动模型。当前任务后续对局可以沿用已确认的目标预设，但会清空上一局追踪器并单独初始化新一局状态；持有、路线和商店状态不跨局沿用。

主要文件：`agent_callbacks.py`、`maa_hook.py`、`bag_preset_reader.py`、`preset_tool.py`、`potential_name_catalog.json`、`character_name_catalog.json`、`bag_preset_rules.json`、`observation.py`、`pool_identity.py`。

### 4. 潜能页：识别候选、估值、选择和刷新

潜能回调沿用原有潜能卡布局、识别参数和卡片选择接口，但把“选择哪张”交给本任务的模型。处理一页时先等待进入稳定候选画面，再读取候选数量、品质、钱包、刷新费用，以及各张卡的名字、旧等级/新等级和推荐标记。`potential_reading.py` 将原始 OCR 和模板结果整理为候选；`ModelPotentialHandler` 再用预设目录、角色范围、品质和已确认持有等级识别每张卡的身份。卡片名称在同一次 OCR 中拼接分行；若多次读取相互矛盾、等级跳变不符合来源规则、页面品质布局变化或钱包数值冲突，则继续等下一帧；仍不能形成完整输入就停止，而不是把不完整读数交给模型。

普通潜能页候选通常属于同一角色，可用队伍目标和旧等级消歧；强化页可能混合角色，代码会比较角色图像和已知持有信息，不会仅因卡片相邻就认定归属。即使名字和品质都相同，只要无法唯一确认角色及潜能身份，就不点击，也不把它写入持有状态。

模型状态包括当前路线位置、金币、已持有等级、目标潜能以及可能的抽取池；决策前要求路线位置和完整潜能身份目录都可用。核心潜能按队伍目标规则优先选择仍有目标等级的卡，不让普通潜能价值模型替代这一专门规则。普通潜能则把当前可选卡与经济上可执行的刷新一起作为候选动作，比较动作对终局普通潜能得分的预期变化并选择价值最高者。该模型的目标是普通潜能收益，不是整局战斗胜率；它没有“最低收益门槛”或置信度拦截。候选日志中的“预期”表示选择后的终局估值，变化行相对于上一次预期；第一次则以开局估值为基准。

若选择结果是刷新，回调把后继临时改为 `星塔_神经网络_潜能刷新`。刷新动作成功返回并不等于页面刷新成功：实现还要确认金币扣减符合刷新费用、候选数量/品质布局重新出现，才增加刷新次数并重新进入潜能识别。本任务把可刷新次数上限设为很大、保留金币设为零，因此实际可刷新性主要由费用是否已确认、当前金币是否付得起及模型对刷新动作的估值决定；无法确认刷新结果会停止本次任务。核心潜能页或强化页等不适用刷新费用的页面不会凭空加入刷新动作。

主要文件：`agent_callbacks.py`、`potential.py`、`potential_reading.py`、`observation.py`、`potential_adapter.py`、`value_model.py`、`critic/`、`tower_sampling_collector.py`。`agent/custom/reco/climb_tower_potential/` 下的上下文、识别参数和卡片布局由原功能提供并复用。刷新和潜能 OCR 辅助定义在 `assets/resource/base/pipeline/climb_tower/climb_tower_neural_potential.json`、`climb_tower_neural_numbers.json` 和 `climb_tower_neural.json`。

### 5. 潜能领取：确认操作后再更新状态

模型识别阶段先选中卡片并暂存一份“待领取”记录，但这时不会更新模型的持有库存。Pipeline 随后进入 `星塔_节点_选择潜能_拿走_agent`；神经网络覆盖把该节点的识别设为 `DirectHit`，由 `stella_value_potential_take`（`PotentialTake`）负责完成真实领取。回调会再次读取卡片页签名、所选卡片和“拿走”按钮，确保屏幕仍是刚才作出决策的同一页；必要时重新选中目标卡，然后点击按钮。

点击后等待原卡页/按钮的消失及下一页的稳定出现，以区分“点击已经发送”与“领取已经发生”。如果新页暂时读不清，会结合原卡和按钮消失、下一页重新出现的证据确认换页；如果原页重新读清，则视为上一次领取未确认，继续有限重试。只有确认离开原页后才提交潜能持有等级、身份池和采样记录；未确认时保留未知状态并停止任务，避免重复领取或把未成功的选择当作已持有。

主要文件：`agent_callbacks.py`、`potential.py`、`potential_reading.py`、`observation.py`、`tower_sampling_collector.py`；领取之后的流程节点仍由 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json` 调度。

### 6. 事件：完整读取菜单后决策，确认点击转换

事件节点 `星塔_节点_进行对话选择_agent` 同时覆盖识别和动作。`stella_value_event`（`Event`）沿用官方事件读取器的区域和选项定位方式，并记录每个问题、选项文字及后果来自哪次 OCR、是否完整。只有完整可见菜单才用于模型决策；选项未显示、文字未读清、后果有缺失或同一菜单读取冲突时会等待重读。事件页不显示楼层，不能把菜单所在时刻当成楼层实读。

普通事件通过事件映射把文字菜单对应到已知事件及游戏选项，再结合当前钱包、潜能状态和路线状态生成可执行选项。模型按各结果概率评估事件选项对后续潜能收益的期望；如果事件楼层存在多条可能路线（例如首层追加事件之后仍可能遇到二层固定事件，二层事件之后才进入三层战斗），会保留多个路线候选并按概率合并估值，而不是挑一个“看起来最像”的楼层。此时决策记录的楼层留空并保留候选；之后的事件奖励潜能页也沿用这些路线候选，不能把估值用的代表路线写成实读楼层。对于随机结果可能造成金币不足、选项已禁用或成本超过当前钱包的选项，会按可执行性排除或标记不评估。

已匹配的答题事件不交给模型选答案，而是按准备阶段载入的官方答案规则匹配问题、选项和后果；答案唯一确认后沿用该规则选择。答题匹配允许当前暂时读不到金币，因为答案本身不依赖钱包；但后续奖励页的余额只用于同步下一次金币变化，不能反推事件楼层。普通事件未映射、模型输入不完整或答题答案未匹配时停止任务，不返回默认选项。

识别器只返回选中选项框，不立即提交事件状态。`stella_note_event_click`（`NoteEventClick`）负责实际点击：若该事件可能消耗音符，会先检查账本是否有可用的操作前库存；缺少可信库存时可导航到背包读取，返回后必须重新识别菜单，核对问题、所有选项和目标选项仍与决策时一致，再使用新框点击。点击后观察事件页稳定关闭或进入后续页，才提交所选事件并清除缓存；点击前的临时模型状态不会因识别成功就提前成为已执行操作。

金币读取以随界面移动的钱包图标定位，避免把展开的音符栏数字当余额；如果 OCR 没提供字框，会先用同帧轮廓定位文字区域，再由 OCR 确认金额。定位框本身不是金额证据。只有同一画面、相互一致的读数才能用于决策；不同读数冲突时不以重试覆盖。候选卡名也只在单次 OCR 内拼接换行，多次读取需要一致才确认身份。

主要文件：`agent_callbacks.py`、`events.py`、`event_reader.py`、`event_mapping.py`、`event_policy.py`、`value_model.py`、`observation.py`、`note_runtime.py`、`note_bag.py`。事件菜单及钱包识别配置位于 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json`、`climb_tower_neural_numbers.json`。

### 7. 商店：将可见货架转换为模型动作

`星塔_节点_商店_商店主流程_agent` 调用 `stella_value_shop`（`Shop`），不运行原版自动购物决策。进入后先确认当前是商店主页面，再确认商店类型和强化费用；进入货架后逐格读取商品名、数量、实际价格和专属角色信息，并读取钱包、剩余刷新次数及刷新费用。缺读时只补齐缺项，不重复执行导航或交易；若整架或关键状态仍不完整，就不构造不完整候选列表。

候选动作包括已确认可买的潜能饮品、符合当前费用的强化、仍有次数且付得起的刷新，以及离店。普通物品不会被错当成模型训练过的购买动作；商店适配器只把可映射的潜能饮品转换为模型支持的购买动作。模型根据从开局累计的路线、已有潜能、库存和金币估算动作收益，不把“进入商店”当成全新开局：首家商店货架完整读出后清除初始标记；最后一层商店内仍处于路线推进阶段（`ADVANCE`），只有离店且路线结束后才转为终局（`END`）。当前冻结的 M213 策略评估潜能饮品、潜能强化等对普通潜能目标的影响，不购买音符。

动作由原 Pipeline 商店子节点执行，神经网络商店逻辑负责决定动作并监督结果。刷新须看到刷新次数减少或确认实际扣费，并读到完整且稳定的新货架；强化后重新确认强化费用和钱包；购买后则等待潜能奖励页，并用商品、奖励和钱包证据关联到本次购买。只有奖励与操作能对应上，才把饮品库存和潜能来源写入模型状态。页面导航或动作结果不能确认时停止，不能把“点击成功”当成交易成功。

主要文件：`agent_callbacks.py`、`shop.py`、`shop_ui/context.py`、`shop_ui/handler.py`、`shop_ui/interactor.py`、`shop_ui/purchase.py`、`purchase_evidence.py`、`potential_adapter.py`、`value_model.py`、`observation.py`、`tower_sampling_collector.py`。商店节点与页面导航仍在 `assets/resource/base/pipeline/climb_tower/climb_tower_agent_sub_shop.json`。

### 8. 结算：读取成绩、潜能数量和音符结果

`星塔_记录界面_读取数值_agent` 将原来的单一保存记录识别扩展为两种条件：原保存文字节点或神经网络专用结算图形。扩展图形识别是为结算按钮文字不可读时保留进入结算读取的机会；随后 `SettlementReader` 再等待结算页面和数据稳定，读取纪录等级及三名角色的潜能数量。潜能数量要先定位三个 UI 数字锚点，再分别进行 OCR 和冲突检查；锚点缺失、读数冲突或与已知字段不一致时将相应值留空，不用部分数字拼出看似完整的总数。

确认后的等级和潜能总数写入原循环节点的 `attach`，以保持原 Pipeline 的结算交接方式。若本地记录未启用或本局尚未确认开始，回调直接委托原有 `RecordScanAction`，避免神经网络采样逻辑改变普通结算行为。记录开启时，读取完成后还会定位结算页的音符标签，点击进入音符结算页并采集最终库存；如果标签或页面转换不能确认，保留缺失状态，不把潜能结算结果当成音符库存。

主要文件：`agent_callbacks.py`、`settlement_reader.py`、`agent/custom/action/climb_tower_record_scan.py`、`settlement_counts.py`、`note_runtime.py`、`tower_sampling_collector.py`；结算保存图形节点位于 `assets/resource/base/pipeline/climb_tower/climb_tower_neural.json`。

### 9. 结果页与音符变化：读取后继续

`星塔_点击空白处关闭_agent` 的动作由 `stella_note_continue`（`NoteContinue`）接管；覆盖还加了一个短暂的界面稳定等待。等待到期只代表应重新观察，并不直接报错或点击。回调重新捕获结果画面，读取音符库存条，并在页面允许时读取楼层。原因是事件奖励页、战斗奖励页和潜能页都可能连续出现，单看“页面出现了”不足以判断音符增量属于哪种来源。

`NoteRuntime` 将快照和待确认来源关联：战斗奖励、事件奖励、连续事件或两者合并的区间分别处理；若一个奖励页无法确认楼层或来源，就不把这段增量强行归给某一场战斗。事件消费音符时，账本先要求操作前库存作为基线，操作确认后再读取后续库存；如果来源只能确定为一个区间，就记录区间而不是伪造单个事件/战斗的精确增量。未知钱包或楼层保持空值。页面采集期间若重新导航，原始继续按钮坐标失效，回调必须在返回页重新识别按钮后再点击；否则使用本帧确认的按钮框。最终等待仍交给框架超时诊断。

主要文件：`agent_callbacks.py`、`note_runtime.py`、`note_ledger.py`、`note_ocr.py`、`note_floor.py`、`ui_flow.py`、`interactor.py`。

### 10. 对局循环：清理边界并控制重复次数

`星塔_循环用节点_agent` 使用 `stella_value_loop`（`TowerLoop`）。每次进入先结束音符账本的本轮边界，并通知采集器归档已结算对局，或将没有结算确认的记录标记为未完成；然后清除本轮潜能追踪器、待领取选择、刷新状态和事件缓存，避免下一局继承上一局状态。目标预设和已加载模型可以保留在任务运行时中。

循环次数来自选项 `神经网络爬塔_爬塔次数` 写入的 `attach.loop_count`。回调把剩余次数减一：还有剩余时更新节点数据并禁用返回主页节点，让原 Pipeline 按既有后继进入下一轮；没有剩余时重新启用返回主页节点，让任务按原流程结束。此逻辑以用户设定次数为准，不依赖结算 OCR 的成功与否；结算识别失败会影响可用记录数据，但不会偷偷改变循环次数。

主要文件：`agent_callbacks.py`、`maa_hook.py`、`note_runtime.py`、`sampling_data.py`；循环节点及其原有后继关系定义在 `assets/resource/base/pipeline/climb_tower/climb_tower_agent.json`。

### 11. 回调共享的运行与记录设施

上述回调由 `agent/custom/action/__init__.py` 接入 Agent 导入链，`climb_tower_neural/__init__.py` 先注册轻量延迟回调，只有任务实际调用且运行环境满足要求时才加载完整运行时、OpenCV 和模型。`maa_hook.py` 维护任务是否属于神经网络模式、模型和每局追踪器；潜能、事件及商店因此可以共享同一份目标、持有、金币与路线状态。

`interactor.py` 与 `ui_flow.py` 通过 Pipeline 统一调度截图、重读和超时；`pages.py` 识别页面类型；`ocr_number.py` 校验数字读数。开启本地记录时，`tower_sampling_collector.py` 将回调里的识别与操作连到 `sampling_data.py`、`sampling_events.py` 和研究数据库模块；是否上传则由任务选项控制，上传实现位于 `sample_upload.py`。这些是多个节点共同依赖的基础设施，不是额外的主流程节点。

## 状态记录、日志与维护约束

模型及业务范围是冻结配置，不应从界面逻辑推断为“自动学会所有策略”：M213 当前按普通潜能终局收益评估潜能选择、可行刷新和潜能饮品/强化，不购买音符；事件使用事件概率与后续潜能价值单独估值，答题使用官方答案规则。预设日志会列出含核心潜能的全队目标和三人的普通潜能分项。候选行的“预期”是所选动作后的终局估值，变化行相对于上一次预期；第一次决策则以开局估值为基准。这些值不是保证达成的收益，也不是战斗胜率。

目录和观测必须严格区分。用于估值的池顺序可以基于潜能目录补全，但需标记为推导/估值信息，不能写成游戏实读池位；钱包或楼层没有可靠证据时留空。批量识别楼层、音符图标或结算协奏卡片时，各轮都检查任务是否停止；中途停止应保留已确认的内容，同时让本轮结算或楼层观测保持不完整。

本地研究数据库只保留推导爬塔状态所需的预设、游戏观测、实际操作、结算和质量标记，不保存截图、逐帧 OCR 或模型估值；对局进行时写临时日志，结算、中断或恢复时才归档。每局使用独立编号，不生成个人或安装标识。数据库 `research.sqlite3` 的四张表为 `presets`、`runs`、`records`、`quality_issues`。归档和恢复以对局为单位避免重复写入；同一对局只由一个 Agent 恢复，写库失败时在后续任务或对局边界重试。

「分享数据，帮助改进模型」默认关闭，且与本地记录分开授权。开启后，结算或中断时将已归档的本局记录通过 `POST https://35.213.73.34/v3/runs` 上传，无需 Token；收尾最多等待 5 秒，未收到回执的授权对局留待之后重试，各局互不阻塞。公开 v3 接收端沿用原 ZIP 信封，`research_wire.py` 标记内容版本；信封里额外的四个旧表名仅为空数组。

更新潜能目录时，用 `python tools/catalogs/tower_catalog.py expand agent/custom/action/climb_tower_neural tmp/tower-catalog` 展开维护目录，更新完成后运行 `python tools/catalogs/tower_catalog.py compact tmp/tower-catalog` 生成发行目录。发行版按潜能 ID 存储，保留中日名称及来源。

M213 权重及移入的推理、模拟代码由 dango636 按本项目的 [MIT 许可](../../../LICENSE) 分发。更换模型时同步更新 [model.json](../../../agent/custom/action/climb_tower_neural/model.json) 中的权重路径、摘要和来源。

## 平台接入与后续维护

当前神经网络爬塔仅支持 Windows x64。平台限制是阶段性状态；发行包的隔离目标是避免在其他平台携带体积较大的 OpenCV 依赖和模型权重，不是删掉整个功能。任务声明、Agent 代码及 Pipeline、图片等资源在各平台包中保留。

### 当前接入点

- `agent/main.py` 导入 `custom`，由 `agent/custom/action/__init__.py` 将神经网络模块接入现有导入链并调用 `register_lazy_callbacks()` 注册轻量回调。无需独立入口或对 `main.py` 做平台分支。
- 注册过程中若发生异常，仅在 OpenCV 可导入且 `model.json` 指定的权重存在时向外抛出；缺少运行依赖或权重的平台会忽略神经网络注册异常，避免阻断普通 Agent。此时神经网络回调可能未注册完整，该平台选择此任务仍可能失败。不要扩大异常捕获范围到普通 Agent 的其他模块。
- 回调实际执行时才尝试导入 `cv2`，并检查 `model.json` 指向的权重文件存在；条件不满足时不加载模型，记录不支持运行环境并停止该次回调。不要在模块导入或 Agent 启动阶段加载 OpenCV 或模型。
- Windows x64 运行依赖由 `assets/requirements-win-x64.txt` 提供。`tools/ci/download_deps.py` 和发行工作流用该清单准备 Windows x64 依赖；其他平台只使用通用 `assets/requirements.txt`。
- `tools/ci/package_common.py` 的 `copy_agent_files()` 在不包含模型的发行目标中读取神经网络目录的 `model.json`，并排除其中 `checkpoint` 指向的文件。更换或移动权重时，以 `model.json` 为路径来源，不要另加硬编码路径；该打包行为有专属测试覆盖。MFA 和 Android 暂存流程按目标平台设置是否包含模型；MXU 是 Windows x64 包，保留权重。其他 Agent 文件及神经网络任务、Pipeline、图片都按通用流程复制。
- Windows x64 的运行依赖清单为 `assets/requirements-win-x64.txt`。`install.yml` 在安装并组装项目后的发行 Python 环境中验证 OpenCV 可导入；这与专属 workflow 在 CI 主机 Python 中运行神经网络测试是两项不同验证。神经网络测试位于 `tools/checks/tower_neural_tests/`，由 `.github/workflows/check-tower-neural.yml` 独立运行。

### 扩展平台时

1. 验证目标平台的 OpenCV wheel、Agent 运行环境及模型推理能力。确认依赖可用后，将 OpenCV 及其必要依赖加入相应平台的发行依赖清单。
2. 在对应发行暂存流程中允许复制 `model.json` 指定的权重。平台行为只需调整 `copy_agent_files()` 的 `include_neural_model` 参数，不要删除任务、Agent 模块或资源文件，也不要改写标准 Agent 入口。
3. 扩展 `.github/workflows/check-tower-neural.yml` 的运行平台/矩阵和依赖准备方式，并在对应发行 workflow 中验证发行 Python 环境能导入 OpenCV；验证回调在有依赖及权重时可启动模型，普通任务在没有 OpenCV 时仍可正常启动。
4. 同步更新[项目结构](../项目结构.md)的平台支持范围、依赖清单和模型打包说明。

### 解除平台限制时

本节只说明如何移除临时的平台容量限制；神经网络爬塔任务、资源、Agent 回调及测试继续保留。是否移除该功能由维护者另行决定。

1. 确认所有目标平台的 OpenCV 及模型推理环境均可用后，在对应打包调用中始终设置 `include_neural_model=True`，再删除 `copy_agent_files()` 中仅为省略权重而添加的选项及按配置排除文件的逻辑。
2. 调整 `tools/ci/download_deps.py` 和发行 workflow 的依赖选择逻辑，将 OpenCV 依赖配置扩展到新支持平台。保留 `install.yml` 中发行 Python 的 OpenCV 导入验证，并将其扩展到相应发行平台；若改由等效的发行包测试覆盖，才移除原验证步骤。普通测试环境中的 `cv2` 检查不能替代发行环境验证。
3. 保留回调实际加载时的 OpenCV/权重检查，作为包内容缺失或安装不完整时的保护；随着平台支持范围变化，重新评估注册异常是否应传播，但不要让神经网络注册错误阻断其他 Agent 模块。
4. 扩展专属 CI 测试平台，并验证各平台发行包均包含权重、发行 Python 能导入 OpenCV，且普通任务不受影响。
5. 同步更新[项目结构](../项目结构.md)中的平台、依赖、权重及发行验证说明。

## 建议优化

本节是维护者对贡献者的建议：
1. 尽量做到对python的opencv库0依赖，因为一个opencv会将星塔助手体积增加100mb(25%)，这对部分用户的影响非常大。
2. 后续改动建议顺便将文件架构定好，方便后续精简代码逻辑。如果能做到后续只用修改固定位置的json文件、神经网络文件就能对新难度或其他服务器的文本适配，而不需要修改其他代码，那就最好了。
