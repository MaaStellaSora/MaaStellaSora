# i18n 维护说明

本文记录项目当前的界面国际化范围、键名约定和检查规则，供后续修改与交接参考。协议字段含义以项目使用的 MaaFramework Project Interface V2 协议为准。

## 当前文件与支持语言

- `assets/interface.json` 声明可用语言及翻译文件路径。
- `zh_cn`、`zh_hant`、`ja_jp`、`en_us`、`ko_kr` 分别使用 `i18n/zh_cn.json`、`i18n/zh_hant.json`、`i18n/ja_jp.json`、`i18n/en_us.json`、`i18n/ko_kr.json`。路径相对于 `assets/`。
- 繁体中文界面与 Agent 日志翻译由 `tools/i18n/convert_to_zh_hant.py` 从简体中文文件全量生成；修改简体中文后重新执行即可覆盖更新。运行前安装依赖：`python -m pip install -r tools/i18n/requirements.txt`，运行命令：`python tools/i18n/convert_to_zh_hant.py`。
- 翻译值是最终显示文本；源文件中以 `$` 开头的值是翻译键。所有已配置 locale 的翻译文件均须包含被引用的键。

## 当前处理范围

当前已处理 `interface.json` 和其 `import` 列表中非服务器特供的任务片段。处理的显示文本包括：

- 项目、控制器和资源的显示标签。控制器与资源显式设置 `label`，其 `name` 继续作为稳定标识。
- 任务、case 和输入项的 `label`。若协议规定没有 `label` 时回退显示 `name`，则显式补上 `label`。
- `description`、`contact` 和输入项的 `pattern_msg`。
- `option` 中已有的 `label`，以及 option、case、input 上的 `description`。

Pipeline 的 i18n 范围包括：

- `assets/resource/` 下正规 Pipeline 节点 `focus` 中的消息文案。
- `interface.json` 导入的非语言专用 task 文件中，`pipeline_override` 节点 `focus` 的消息文案。
- `focus` 的字符串写法，以及对象写法中的 `content`。消息类型键、节点名和模板占位符是协议标识或运行时变量，不翻译。

Python Agent 日志使用独立的 `agent/agent_config/i18n/<locale>.json` 翻译文件，不与 `assets/i18n/` 共用键空间。Agent logger 根据 `PI_CLIENT_LANGUAGE` 读取语言；`zh_cn.json` 是必需的基础回退文件，`zh_hant.json`、`ja_jp.json`、`en_us.json`、`ko_kr.json` 分别提供繁体中文、日文、英文和韩文日志翻译。所有日志级别在运行时都经过相同的翻译处理；检查器只扫描 `info`、`warning`、`error`，不扫描 `debug`。以 `$agent.` 开头的日志消息按键翻译，含中文的硬编码日志会被检查器报告。

日志运行时不按级别分支，避免同一套翻译逻辑因日志级别不同而表现不一致；检查器则只覆盖需要迁移的 `info`、`warning`、`error` 业务日志，`debug` 不作为本轮文案迁移与静态检查范围。因此，`debug` 虽可使用翻译键，但不会由检查器验证。

文件名以语言后缀结尾的 JSON（如 `_cn`、`_tw`、`_jp`、`_en`、`_kr`）不纳入 task 或 Pipeline 扫描；例如 `invite_select_cn.json` 不处理。

`option` 映射中的键（例如 `option` 下的 `"作战关卡"`）是配置项标识，不是显示文本。该对象没有 `name` 字段，若没有 `label`，当前 Client 不显示配置项标题，因此不为它凭空添加 `label`。如后续 Client 的显示行为改变，应重新确认这一约定。

以下内容不做 i18n：

- `welcome` 暂时保留原文，是否国际化待后续决定。
- `default` 是配置值，不是显示文案。它通常引用 `name`，改成翻译文本可能影响选项匹配或运行逻辑。
- 英文或数字文案可直接保留，例如 `MaaStellaSora`、`PlayCover`、`Yes` 和 `No`。对 `Yes` / `No` case，如需显式补 `label`，保留对应英文值；不要修改用于开关判断的 `name`。
- `custom_title` 使用 `"MaaStellaSora"`，不走翻译。
- `name`、option 键、case `name`、input `name` 等被任务配置和 Pipeline 引用的标识保持不变。翻译只放在 `label` 等显示字段中。
- 带语言后缀 `_cn`、`_tw`、`_jp`、`_en` 或 `_kr` 的导入文件不进入公共界面翻译检查。
- 没有出现在 `interface.json.import` 中的 task 片段文件不处理。若后续将其加入导入列表，检查器会自动纳入（带上述语言后缀的文件除外）。

## 键名约定

键采用点分段结构。键由稳定的界面对象标识与字段路径组成，而不是由翻译后的文案组成。例如：

```text
interface.description
interface.controller.桌面端.label
interface.resource.官服.label
interface.task.登录游戏.label
interface.task.登录游戏.description
interface.task.option.邀约旅人.inputs.1号.label
interface.task.option.邀约旅人_1号_送礼.cases.所有.label
pipeline.猎影合围_任务完成.focus.Node.Action.Succeeded
interface.task.option.真格挑战_选择首领.cases.真格挑战_选择首领_首领1.pipeline_override.真格挑战_有挑战次数时选择首领.focus.Node.Action.Succeeded
```

对应的源字段引用以 `$` 开头，例如：

```json
{
    "name": "登录游戏",
    "label": "$interface.task.登录游戏.label",
    "description": "$interface.task.登录游戏.description"
}
```

Pipeline 的 `focus` 消息文案使用相同的 `$` 引用方式。正规 Pipeline 键由节点名和消息类型构成；覆盖节点键还包含 option、case（若有）及 `pipeline_override` 路径，避免不同选项覆盖同名节点时发生键冲突：

```json
{
    "focus": {
        "Node.Action.Succeeded": "$pipeline.猎影合围_任务完成.focus.Node.Action.Succeeded"
    }
}
```

`assets/i18n/zh_cn.json` 中只写不带 `$` 的键：

```json
{
    "interface.task.登录游戏.label": "登录游戏",
    "interface.task.登录游戏.description": "自动登录游戏，并且关闭活动弹窗以及签到弹窗"
}
```

Agent 日志也使用稳定的点分段键，通常按 `agent.<模块路径>.<函数或事件>.<语义>` 组织；源码日志以 `$` 加键名引用，翻译文件中则省略 `$`。例如：

```python
logger.warning(
    "$agent.custom.action.example.load_failed",
    {"filename": filename, "reason": reason},
)
```

```json
{
    "agent.custom.action.example.load_failed": "读取 {filename} 失败：{reason}"
}
```

需要动态值时，将变量以映射作为日志参数传入，并在翻译文本中使用 `{变量名}`；不要在日志调用处先用 f-string 拼接文案，这样翻译可调整变量位置。各语言翻译必须保留对应变量名，确保映射中提供了所有占位符。当前检查器不校验占位符的一致性，需要维护者自行核对。

添加或修改显示文本时，应同步更新源字段和所有已配置语言文件。若更改了用于构造键名的 `name` 或 option 键，应同步迁移引用和翻译文件中的键；除非本身确实要改变标识，不要为了翻译而改标识。

当前键使用原始 `name` / option 键作为路径段，便于从配置定位翻译项。若未来这些标识包含点号，点分段会产生歧义；届时应先约定统一的转义或结构化键规则，再批量迁移，避免各处自行转义。

## 检查脚本

运行：

```powershell
python tools/checks/check_i18n.py
```

脚本 `tools/checks/check_i18n.py` 当前会：

1. 扫描 `interface.json`、其实际导入且非语言专用的 task 文件、`assets/resource/` 下的 Pipeline JSON，以及 Agent Python 文件中的 info/warning/error 日志。
2. 对界面可国际化字段、Pipeline `focus` 文案及 Agent 日志检查未替换的中文硬编码；也检查会回退显示中文 `name`、但没有显式 `label` 的对象。
3. 从界面字段、task `pipeline_override`、正规 Pipeline `focus` 和 Agent 日志中收集 `$key` 引用。界面与 Pipeline 键由 `assets/interface.json.languages` 指定的翻译文件覆盖；Agent 键由 `agent/agent_config/i18n/<locale>.json` 独立覆盖，且必须包含 `zh_cn.json`。两类翻译文件均检查缺失键和未被引用的多余键；翻译值必须是字符串，重复 JSON 键也会报错。
4. 对 Pipeline `focus` 同时识别字符串形式和对象形式的 `content`；对 Agent 仅检查 info/warning/error，debug 及其他 Pipeline 字段（例如节点名、识别参数和流程引用）不作为显示文本扫描。
5. 支持检查器所读取 JSON 中的注释和尾随逗号，路径以项目根目录为基准。

增加语言后，每个对应语言文件都需要包含当前所有被引用的键；键不全或残留未引用键会使检查失败。脚本不检查 `welcome` 中的硬编码中文，也不会把任意中文字符串都判为错误，只检查约定的界面显示字段、Pipeline `focus`、Agent info/warning/error 日志和 `name` 回退场景。

检查范围通过 `CHECK_SCOPES` 扩展。各扫描器实现 `CheckScope` 协议，返回显示文本中的键引用和问题；界面/Pipeline 与 Agent 分别针对各自的 locale 文件做键覆盖检查。新增检查范围时优先添加独立扫描器，避免扩大通用遍历逻辑的复杂度。

## Agent 日志维护规则

- 新增或修改需要本地化的日志时，在对应源码使用 `$agent.<模块路径>.<函数或事件>.<语义>`，并在 `agent/agent_config/i18n/zh_cn.json` 增加不带 `$` 的键和值。纯英文日志保留原文。
- `PI_CLIENT_LANGUAGE` 对应的语言文件会覆盖 `zh_cn.json` 中的同名键；未提供或无法读取其他语言文件时仍使用简体中文翻译。当前提供 `zh_hant.json`、`ja_jp.json`、`en_us.json` 和 `ko_kr.json` 覆盖文件。若键在可用翻译中都不存在，日志按原始消息输出，不因翻译文件读取失败而中断。
- 日志格式中的 `{变量名}` 使用 `logger.<level>("$key", {"变量名": value})` 传值。翻译时可以调整占位符位置，但必须保留变量名，并确认每次调用都提供所需变量。
- 日志文件格式包含 i18n 键字段，普通日志为 `-`，已翻译日志记录实际键名；排查日志时可用该键定位翻译条目。
- 检查器只覆盖 `logger.info`、`logger.warning`、`logger.error` 的静态消息，以及当前 `_handle_fatal_error` 的静态键参数；不要依赖它检查 `debug`、动态构造的消息或占位符是否匹配。
- Agent 翻译与界面/Pipeline 翻译分开维护：前者由 Agent logger 根据 `PI_CLIENT_LANGUAGE` 加载，后者由 `assets/interface.json.languages` 声明；两者加载入口和语言配置独立，因此不合并键空间。新增 Agent 语言文件时使用 locale 名称作为文件名（例如 `ja_jp.json`），并保持与 `zh_cn.json` 引用键覆盖一致。

## 后续维护建议

- 新增可显示的中文文案时，优先使用协议支持的国际化字段，并为所有已配置翻译文件增加对应键。
- 新增或修改 Pipeline `focus` 文案时，在源 JSON 中引用稳定的 i18n 键，并同步更新各 locale 翻译文件；不要翻译节点名、消息类型或模板占位符。
- 新增带 `name` 的任务、case、输入项等对象时，判断协议和 Client 是否会在缺少 `label` 时回退显示 `name`；若会，显式设置 `label`。
- 新增按语言区分的 task 或 Pipeline JSON 时，使用 `_cn`、`_tw`、`_jp`、`_en`、`_kr` 等后缀；若增加新的语言后缀，同步更新检查器的 `LANGUAGE_SUFFIX`。
- 每次修改后运行 i18n 检查，并在新增语言时确认所有 locale 都通过。
